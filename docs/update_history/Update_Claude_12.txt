You’re right to flag it—those 10× smaller “best” lengths (46,493 on pr2392; 37,943 on fnl4461) scream evaluation path mismatch. Multi-hive is almost certainly summing on normalized coords / synthetic scale, while single-hive uses the TSPLIB integer metric. The controller looks fine (epochs, UCB1, hive diversity) — it’s the units that broke your A/B.

What I think happened

In multi-hive, the solver (or logger) is using the feature-normalized coordinates (centered + RMS/divided) or a synthetic loader’s scale to compute/record best_len.

Single-hive is using the raw TSPLIB metric (EUC/ATT/CEIL with integer rounding).

Result: same tour quality, totally different units → multi-hive numbers ~4–10× smaller, “beating opt” by nonsense factors.
